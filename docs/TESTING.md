# 테스트 전략과 성능 실험

2026-09-20 작성. 현재 증거와 후속 구현 계획을 구분한다.

## 테스트로 설명할 개발 과정

이 프로젝트에서는 실패 조건 정의 → 재현 테스트 → 원인 분석 → 변경 → 회귀 검사 →
결과 기록을 보여준다. SK하이닉스 DAM의 데이터 품질·통합테스트 경험과 삼성전자의
운영 문제 분석 경험을 개인 CUDA 프로젝트에서 어떻게 적용했는지 설명하는 근거로 사용한다.
기존 직장 프로젝트의 수치나 성과를 이 프로젝트의 성과로 옮겨 적지 않는다.

현재 CUDA 프로젝트에서 입증한 것은 정상/소프트웨어 오류 주입 판정과 CPU 대조다.
성능 개선은 아직 측정하지 않았다. 이미 만든 코드를 사후에 테스트한 이력을
처음부터 테스트 우선으로 개발한 것처럼 표현하지 않는다. 앞으로의 결함 수정에서는
재현 테스트와 수정 전후 결과를 함께 남긴다.

## CPU 대조 분리 단계의 자동 검사

현재 [CPU 단위 테스트](../tests/unit/test_reference.cpp) 15개를 CTest에 등록했다.
GPU·CUDA Toolkit 없이 빌드하고 실행한다. [새 CLI 검사](../tests/cli/test_validator.py)는
실제 GPU에서 새 실행 파일의 세 경우를 기존 `check_output()` 기준으로 확인한다.

- 정상 패턴, GPU 기록 순서 변경, 임의의 유효한 잘린 부분집합, 기록 한도 0, 한 원소.
- 잘못된 오류 개수·actual·expected, 중복 위치, 범위 밖 위치, 정상 원소를 오류로 보고.
- 한도 내 기록 누락, 한도 초과 기록, 기록 한도 0인데 상세 기록이 존재하는 경우.
- 앞선 대조 실패가 다음 호출 결과에 남지 않는지 확인.

새 reference 모듈은 기록 수 계약을 명시적으로 확인하고 CPU 상세 기록도 제한한다.
기존 고정 설정의 정상/주입 결과는 유지한다. CPU 모듈에서 한도 0·2를 시험한 것은
그 설정의 실제 GPU 메모리 기록 경로까지 자동 시험했다는 의미는 아니다.

## CLI·출력 분리 단계 — 2026-09-21

기존 CPU 대조 15개에 [CLI·상태 판정 검사](../tests/unit/test_application.cpp) 5개를 추가해
총 20개의 CPU 단위 테스트를 실행한다. 기본 인자, `--inject`, 알 수 없는 옵션,
중복/불필요한 인자를 확인하고, 전체 실행 상태의 모든 두 상태 조합에서
ERROR > FAIL > PASS 우선순위를 검사한다.

GPU CLI 세 경우의 `check_output()` 검사 기준은 변경하지 않았다. 새 main이 CLI,
GPU 실행, 출력 모듈을 연결한 실제 실행 파일에서 이를 통과했다. 출력 포맷을
모듈별로 복제한 단위 테스트를 추가하지 않고 기존 전체 경로 검사를 활용했다.

## 책임 분리와 함께 만들 테스트

아래 계층 중 CPU 대조와 기본 CLI 검사는 구현했고 나머지는 후속 목표다. 테스트를 위해 CUDA 커널을
CPU 모의 구현으로 대체하지 않는다. CPU만으로 판단할 수 있는 로직과 실제 GPU 실행을 분리한다.

| 계층 / 경로 | 검사할 계약 | 잡으려는 문제 |
| --- | --- | --- |
| CPU 단위 검사 / `tests/unit/` | 입력 파싱·크기 계산·주입 위치 선택 | 음수/0/overflow 수용, 작은 배열의 중복 XOR 상쇄 |
| CPU 단위 검사 / `tests/unit/` | reference의 개수·값·범위·중복 판정 | count만 맞는 잘못된 기록, 중복/범위 밖 index를 정상 취급 |
| GPU 통합 검사 / `tests/gpu/` | fill → injection → verify → 복사 | 누락, tail 처리, 카운터 잔존, 오류 기록 한도 위반 |
| CLI 회귀 검사 / `tests/cli/` | 입력·최종 결과·종료 코드·원시 로그 | 앞선 FAIL이 뒤의 PASS로 덮임, ERROR가 PASS로 기록됨 |
| 성능 실험 / `benchmarks/` | 같은 작업의 변경 전후 시간과 결과 | 측정 범위 혼동, 검사 생략을 동일 작업 최적화로 오인 |

함수 호출 여부나 단순 전달 함수마다 테스트를 추가하기보다 위 실패 조건을 검사한다.
CPU 단위 검사는 GPU 없이 실행할 수 있도록 reference와 CLI를 CUDA API로부터 분리한다.
GPU가 없는 환경은 GPU 검사를 SKIP/미실행으로 표시한다. 일반 CI의 CPU 검사 통과를
GPU 검사 통과로 표현하지 않는다. CI와 GPU 자동 실행 환경은 아직 구성하지 않았다.

우선 자동화할 사례:

1. 원소 수 1·2·255·256·257·1025에서 정상 검사와 주입 검사.
2. 자동 주입 위치가 겹치면 한 위치를 한 번만 변조. 예: count=1의 index 0에 mask 1 한 번.
3. 오류 3건에서 기록 한도 0·2·3·4: 전체 count와 기록 수, 잘림 여부, 기록 내용 확인.
4. 주입 패턴/iteration 이후 정상 검사에서 count와 유효 기록 수 초기화.
5. reference에 의도적으로 잘못된 actual·expected, 중복·범위 밖 index, 잘못된 count 전달.
6. 기록 순서는 달라도 같은 결과로 인정하며, 중복·누락은 실패 처리.
7. 잘못된 인자, 범위 밖 주입 위치, 숫자 overflow는 명확한 ERROR로 종료.

기록 한도보다 오류가 많을 때 어떤 index가 기록되는지는 GPU 실행 순서에 따라 달라진다.
전체 오류 count를 확인하고, 저장된 기록이 실제 오류 집합의 중복 없는 부분집합인지 검사한다.
한도가 충분할 때는 전체 오류 집합과 정확히 일치해야 한다.

CPU 기대값은 GPU 계산 결과를 그대로 정답으로 사용하지 않는다. 알려진 입력·주입 mask와
독립적인 CPU 계산으로 확인한다. 기능 검사의 tail 결과가 맞아도 불법 메모리 접근이
전혀 없음을 증명한 것은 아니므로 Sanitizer의 미검증 상태는 별도로 유지한다.

## 첫 성능 실험 후보: CPU 검사 버퍼 재사용

현재 예제는 패턴마다 `host_data`와 CPU 기록 중복 검사용 버퍼를 생성한다.
큰 배열을 반복 검사할 때 이 생성·초기화 비용이 전체 시간에 영향을 주는지 측정한다.
실제로 존재하는 기준 구현을 사용하며 비교를 위해 느린 경로를 새로 만들지 않는다.

후보 변경은 버퍼를 검사 실행 동안 재사용하는 것이다. CPU 전체 대조, GPU 검사,
패턴, 오류 주입 조건과 결과 기록 범위를 모두 유지한다. 재사용 시 이전 값이 남는
문제는 주입 후 정상 검사와 기존 회귀 검사로 확인한다.

측정 절차:

1. 책임 분리 후 정확성 검사를 통과한 commit을 기준 버전으로 고정한다.
2. 기준 버전과 변경 버전을 동일 컴파일 옵션으로 준비한다.
3. 동일 GPU·원소 수·패턴·iteration·주입 조건·기록 한도·CPU 대조 모드로 실행한다.
4. 준비 실행 후 10회 이상 측정하고 원시 표본·중앙값·최소/최대 또는 사분위 범위를 저장한다.
   기준/변경 버전을 번갈아 측정해 실행 순서에 따른 온도·부하 차이도 살펴본다.
5. 검사 전체 시간과 GPU 구간 시간을 구분한다. 동일한 출력 설정을 적용하며,
   초기 할당과 마지막 해제를 포함한 전체 시간도 함께 남겨 비용을 밖으로 옮긴 효과를 구분한다.
6. 변경 전후 정확성 결과를 다시 대조하고, 실행 간 변동을 고려해 개선 여부를 판단한다.

비동기 커널 launch 호출만 CPU 시계로 잰 값을 GPU 실행 시간으로 쓰지 않는다.
GPU 구간은 CUDA events와 완료 대기를 사용하고, host 구간은 완료가 포함된 경계를
정의한다. 시간 측정 근거는 아래 NVIDIA 문서를 따른다.

CPU 전체 대조를 끄거나 기록량을 줄여 빨라진 결과는 서로 다른 검사 모드의 비용 비교다.
같은 검증을 유지한 성능 개선 결과와 구분한다. 개선이 미미하거나 느려졌으면 원시 결과와
판단을 기록하고, 성능 개선 수치를 자기소개서에 추가하지 않는다.

성능 실험은 정확성 검사와 별도 명령으로 실행한다. 공유 GPU의 실행 시간을 일반 테스트의
고정 PASS/FAIL 임계값으로 사용하지 않는다. 실제 병목 측정 결과가 다른 곳을 가리키면
그 결과에 따라 첫 최적화 후보를 변경한다.

## 포트폴리오에 보여줄 증거

README에 다음 순서로 연결한다.

- **문제**: 재현 조건, 기대 결과, 실제 실패 결과.
- **테스트**: 어떤 결함을 잡는지 설명하는 이름과 실행 명령.
- **변경**: 원인과 수정 내용, 해당 commit.
- **검증**: 수정 전후 결과 및 기존 기능 회귀 검사.
- **성능**: 실험한 경우에만 조건·원시 표본·비교 표·해석을 추가.

작은 배열의 중복 주입 문제는 첫 사례 후보다. 현재 고정 count에서는 발생하지 않으며,
크기 설정을 도입할 때 재현 테스트로 확인한 뒤 수정 전후 증거를 남긴다.
성능 사례도 실제 측정이 완료된 뒤 같은 형식으로 작성한다.

새 기능의 기대 동작과 테스트를 먼저 정의하고, 기능과 테스트를 함께 커밋한다.
결함 수정의 실패 로그는 보존하되, 실패하는 테스트만으로 기본 브랜치를 남겨 두는 것을
필수 절차로 삼지는 않는다. 테스트 개수나 커버리지 수치를 목표로 기능을 늘리지 않는다.

## 목적과 결과물

CUDA 기반 GPU 메모리 검증·오류 분석 실험 도구를 만든다. 지정한 GPU 메모리 영역에
패턴을 쓰고 검사하며, 소프트웨어로 주입한 오류를 재현·검출·기록하고 반복 실행 결과를 남긴다.
SK하이닉스 Software 지원 포트폴리오에서는 기존 DRAM 검증 및 운영 SW 경험을
새로운 실행 환경에 적용하는 과정과 검증 도구 자체의 정확성 확보 방법을 설명한다.

제출 결과물은 CLI 실행 파일, 재현 가능한 빌드와 테스트, 실제 실행 기록,
설계·관찰 결과·한계를 설명하는 README 및 첨부용 요약 PDF다.
자세한 날짜·시간 배분은 상위 작업 공간의 `SK_hynix_GPU_HBM_plan.md`를 따른다.

테스트를 개발 과정의 주요 결과물로 관리한다. 현재 검증 증거, 테스트 계층,
성능 측정 조건은 [테스트 전략과 성능 실험](TESTING.md)을 따른다.

| --- | --- | --- |
| 네 가지 32-bit 상수 패턴 | 구현 | 각 패턴의 정상 결과와 주입 결과 재현 |
| fill / injection / verify 분리 | 구현 | 동일 stream의 실행 순서와 tail 경계 유지 |
| GPU 오류 개수와 최대 K건 기록 | 설정 가능, K=0/1/2/3/4 자동 검사 | K를 설정 가능하게 하고 초과·동일·0건 조건 자동 검사 |
| CPU 독립 대조 | CUDA 독립 모듈과 15개 단위 검사 구현 | 작은 배열은 전체 대조, 큰 실행은 명시적으로 생략 가능 |
| 입력 설정 | count/K/iterations 및 입력 검사 구현; CPU 대조 모드는 전체 검사 고정 | 양수 원소 수, 기록 한도, 반복 횟수, CPU 대조 모드 설정 |
| 주입 위치 | 처음/가운데/끝, 중복 제거 구현 | 처음·가운데·끝 자동 선택 시 중복 제거; 지정 index와 mask로 재현 |
| 반복 실행 | 사용자 지정 횟수, 초기화·상태 유지 구현 | iteration별 초기화, 결과 구분, 앞선 실패 유지 |
| 상태·종료 코드 | PASS=0 / FAIL=1 / ERROR=2 및 부분 결과·오류 원인 보존 구현 | 사용자 중단도 PASS로 기록하지 않도록 확장 |
| 회귀 테스트 | CPU 단위 25개, 런타임·버퍼 10개, CLI 26개 자동화 | GPU 크기·기록 한도·반복·잘못된 입력·대조 오류를 자동 확인 |
| 실험 실행기 | 환경·설정·코드/바이너리 해시·시간·원시 로그·중단 원인 저장 구현 | 실험 설정·코드 버전·환경·시간·원시 결과를 실행 ID로 묶기 |
| 모니터링 | nvidia-smi 주기 조회, 지표별 가용성 구분 구현 | 제공되는 nvidia-smi 지표 수집, N/A와 수집 실패를 구분 |
| 문서·제출 자료 | README와 기록 구현 | 한 명령 재현, 결과 해석, 관찰 범위, 첨부용 요약 |

`--inject`는 첫 iteration의 첫 패턴에만 주입한다. 반복은 1~10000회이며
현재 결과를 끝까지 보관하는 구조에 맞춘 상한이다. 사용자 지정 index/mask, CPU 대조 생략,
C++ 내부의 중단 처리와 점진적 저장은 후속 범위다. Python 실행기의 timeout/SIGINT/SIGTERM 처리는 구현했다.

입력은 `count=0`, 음수, 잘못된 숫자, 범위 밖 주입 위치, 바이트 수 곱셈 overflow를
실행 전에 거부한다. `max_records=0`은 오류 개수만 세는 모드로 정의한다.
현재 unsigned int 오류 카운터의 표현 범위를 넘어서는 원소 수도 허용하지 않는다.

작은 회귀 검사는 기본 1,025개 원소를 유지한다. 큰 실험은 기존 계획에 따라
128~256 MiB에서 시작하고 당시 여유 메모리를 확인해 단계적으로 늘린다.
검사하는 것은 해당 실행에서 할당한 영역이다.

CPU 전체 대조를 생략한 실행에는 `reference_check=SKIPPED`를 기록한다.
이는 GPU 검사 전체의 PASS/FAIL과 별도 항목이다. 텔레메트리 미지원도 검증 성공으로
치환하지 않고 개별 항목의 가용성으로 표시한다.

## 추가 실험과 제한

필수 범위가 안정된 뒤 시간 안에서 index/seed 패턴, 별도 메모리 대역폭 실험,
작은 PyTorch 워크로드 오류 분석을 추가할 수 있다. 모두 현재 미완료 항목이다.
검증 커널의 비교·atomic 기록 시간을 순수 메모리 대역폭으로 표현하지 않는다.

이번 제출에서는 multi-GPU, driver/firmware 구현, 물리 셀 불량 판정, 장비 대여,
대규모 서비스·DB·대시보드 구축까지 확장하지 않는다. RTX 3060은 GDDR6 환경이며,
XOR 오류 주입은 검출 경로를 확인하는 소프트웨어 실험이다. HBM 실측이나 HW fault
주입 경험으로 표현하지 않는다. Compute Sanitizer는 현재 WDDM 환경 오류로 미검증이다.

## 현재 구조에 대한 판단

단일 파일은 host/device, 실행 순서, 오류 확인을 학습하기 위한 초기 예제로 사용했다.
초기 main은 CLI, 메모리 할당·해제, 패턴 순회, 커널 실행, CPU 대조, 로그 출력까지
담당했다. 현재는 main이 일반 C++ API를 연결하고 각 모듈이 해당 책임을 수행한다.
입력·출력 변경과 검증 알고리즘 변경을 독립적으로 확인할 수 있는 구조로 옮겼다.

CUDA가 main 집중 구조를 요구하는 것은 아니다. CUDA 코드를 담은 번역 단위와 일반
C++ 번역 단위를 나눌 수 있다. GPU가 호출하는 device 함수 자체를 번역 단위 간에
나누는 경우에는 별도 device linking 고려가 필요하다. 처음에는 모든 커널과 launch를
하나의 `.cu`에 유지하여 그런 구성이 필요 없는 구조로 시작한다.

## 제안하는 모듈 구조

```text
CMakeLists.txt
include/gmv/
  types.hpp                 # Config, ErrorRecord, PatternResult, RunResult, Status
  cli.hpp
  validator.hpp
  reference.hpp
  report.hpp
src/
  main.cpp                  # 설정 읽기 → 실행 → 출력 → 종료 코드
  cli.cpp                   # 인자 파싱, 입력 검증, 사용법
  validator.cu              # GPU 자원 수명, 커널, 패턴/iteration 실행과 결과 수집
  reference.cpp             # CPU 기대값 검사, GPU 기록 대조
  report.cpp                # 결과 객체를 콘솔/구조화 로그로 표현
scripts/
  setup_cuda.py             # 개발 환경 준비
  test_first_kernel.py      # 기존 학습 예제의 회귀 기준
  run_experiment.py         # 환경·반복 실험·모니터링
tests/
  unit/                     # GPU 없이 입력·CPU 대조 로직 검사
  gpu/                      # 실제 GPU 커널과 자원·반복 동작 검사
  cli/                      # 새 실행 파일의 출력·종료 코드 회귀 검사
benchmarks/                 # 동일 조건의 변경 전후 성능 실험
examples/
  first_kernel.cu           # 현재 학습 예제를 기준 버전으로 보존
docs/
  PROJECT.md
results/
  README.md                 # 선택한 실행 증거 목록
```

위 트리는 목표 구조다. 미구현 모듈의 빈 파일이나 실행기를 미리 만들지 않는다.
학습 예제는 보존하되 새 기능은 `src/`의 도구에만 추가하여 구현 두 벌을 계속 관리하지 않는다.

책임 경계:

- `main`: 최상위 실행 흐름과 예외 처리. 커널 launch나 원소 검사 루프를 두지 않는다.
- `cli`: GPU 없이 검증 가능한 입력 처리. GPU의 실제 여유 메모리 등 환경 의존 검사는 validator가 한다.
- `validator`: 할당한 자원을 소유하고 fill → injection → verify → 결과 수집을 수행한다.
  kernel은 파일 내부에 두고 외부에는 일반 C++ 호출 형태의 실행 함수를 제공한다.
- `reference`: CUDA 헤더나 API에 의존하지 않는 CPU 함수. 원본 값과 GPU 기록을 받아
  개수·내용·범위·중복을 검사한다. GPU와 잘못된 기대값 계산을 공유하지 않도록 기준을 유지한다.
- `report`: 검사 판단을 새로 만들지 않고 결과를 표현한다. CPU 대조 여부와 기록 잘림을 명시한다.
- `types`: 공유하는 작은 데이터 구조. CUDA device 포인터를 CLI·출력 계층으로 노출하지 않는다.
- Python 테스트와 실험 실행기: 예상 결과를 판정하는 테스트와 관찰 결과를 저장하는 실험을 구분한다.

단순 struct와 함수부터 시작한다. GPU 버퍼처럼 소유권이 있는 자원에만 RAII를 사용하고,
모든 모듈을 클래스·상속 계층으로 만들지 않는다. `validator.cu`가 커지면 GPU backend와
패턴 순회를 분리할 수 있지만 현재 세 커널을 각각 파일로 나누지는 않는다.

## 오류·자원 관리 원칙

기존 CUDA_CHECK의 `std::exit(2)`를 예외 전달로 변경했다. CUDA 실행 경계에서
오류를 결과 객체에 기록하고 main이 ERROR/종료 코드 2를 반환한다.
DeviceBuffer는 예외로 범위를 벗어날 때도 이미 소유한 버퍼의 해제를 시도한다.
소멸자는 예외를 던지지 않고 해제 오류 코드를 별도 상태로 남긴다.
할당·복사·launch·실행 중 오류를 데이터 mismatch로 변환하지 않는다.

여러 패턴 중 하나라도 FAIL이면 전체 FAIL이다. 실행/대조 ERROR가 있으면 ERROR를 우선한다.
큰 실험 결과는 실행기에서 단계별로 저장하여 중단 시에도 완료된 검사와 미완료 부분을 구분한다.

현재 모든 iteration/pattern의 결과는 host 결과 객체에 모아 정상 종료 또는 처리 가능한 오류 이후 출력한다.
오류가 나기 전에 완료한 패턴은 유지하고, 진행 중이던 패턴은 완료 목록에 넣지 않는다.
실행 오류와 해제 중 오류는 서로 덮어쓰지 않는다. 사용자 신호·강제 종료에 대한
부분 결과 영속화와 장시간 실행 중 점진적 저장은 아직 미구현이다.

내부 `CudaRuntime`의 할당·해제·동기화 경계만 테스트에서 교체할 수 있다.
실제 커널과 데이터 복사를 CPU 모의 구현으로 대체하지 않는다. 반환값 주입은
프로그램의 오류 처리 검증이며 실제 OOM·하드웨어 장애·CUDA context 복구를 입증하지 않는다.

## 구현과 커밋 순서

1. **설계 기록(이번 변경)**: 범위·현재 상태·책임 분리를 문서화한다.
2. **책임 분리**: 현재 동작을 새 구조로 옮긴다. 인자·패턴·출력·종료 코드는 유지한다.
   CMake 빌드와 기존 3개 경우의 검사 기준을 연결하고, 예제와 새 실행 파일을 같은 기준으로 확인한다.
   CPU 대조를 분리하면서 잘못된 기록을 거부하는 수동 사례도 자동 검사로 옮긴다.
3. **자원·오류 처리**: RAII와 오류 전달을 정리한다. 필요한 할당 실패·오류 경로를 검증한다.
4. **설정·경계 조건**: count와 기록 한도를 설정 가능하게 하고 주입 위치 중복을 제거한다.
   1·2·255·256·257·1025개 원소, 한도 0·2·3, 잘못된 입력을 자동 검사한다.
5. **반복·실험 기록**: iteration과 주입 조건을 명시하고 실행기·모니터링을 연결한다.
   정확성이 고정되면 동일 검사 조건에서 성능 기준을 측정하고, 측정한 병목의 변경 전후를 비교한다.
6. **제출 자료**: 완료한 사실과 원시 실행 결과를 README 및 요약 PDF로 정리한다.

사용자의 최신 진행 방식에 따라 Codex가 단계별 구현·검사·커밋을 수행하고,
변경 의도·결과·직접 실행 명령을 설명한다. 사용자는 필요할 때 실행해 보고
중요한 개념의 퀴즈로 이해를 확인한다. 설명을 위한 사용자 확인을 커밋 승인 절차로 삼지 않는다.
책임 분리와 새로운 검사 기능을 한 커밋에 섞지 않는다. 기존 자동 검사 기준은
새 디렉터리 구조로 옮기기 위해 필요한 빌드 경로 변경 외에는 완화하지 않는다.
